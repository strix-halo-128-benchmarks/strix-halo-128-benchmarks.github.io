Change log — every version, and why it changed

Contents

    This document's history, kept separate from the report so the report can stay about the measurement. Each entry states what changed and the numbers that forced the change; a correction is only worth anything if it records what was wrong before it.

    Versions before 1.3 are summarised compactly: they predate the build register (§4.1), the cap discipline (§7.2) and the provenance manifest (§20.5), and their numbers should be read with those absences in mind.

    The cap is the finding, not a footnote. Seven of the eleven are non-thinking arms and were measured at a 512-token generation cap on both capability axes — the budget a 16 GiB card leaves after weights and KV — so their cells describe what the card delivers, not the model's ceiling. The three that deliberate were re-run at 4096-8192 for that reason: lfm25-24b-a2b reads MMLU 0.1917 at 512 and 0.6917 at 4096 on the same weights, which is a 50-point swing produced entirely by the cap, and it is the clearest single illustration on this box of why cap discipline outranks model choice in a benchmark comparison. gemma-4-26B-A4B-QAT and base lfm25-24b-a2b already had rows here at 2048 and 4096, so those files appear once, at their better run; their 512-cap numbers stay on the 16 GiB page as the cap evidence.

    What moved as a result. lfm25-24b-a2b (thinking) takes the top HumanEval cell in Table 4 at 0.9695 (159/164), ahead of gemma4-31b at 0.9634 (retired 2026-10-30) — so the best-coding row on the board is now a 12.65 GiB file that is also the second-fastest decoder measured here. §11.3 gains it at 111.2 t/s (second only to mellum21-fork at 111.9) and §11.4 grows from 8 rows with all fourteen riddles to 16. The counts are recounted from the archive rather than inherited: 206 runs, 75.2 h, 87 aliases, 48 matrix rows, 29 rows still servable on disk — §0.3, §9's preamble and §18.3 now say those numbers, and the roster header cites files on disk (49 .gguf, 807.6 GiB, checked 2026-11-12) instead of a family count that three different readings of the directory could give three different answers for.

    Not in this edition: Clover-35B-A3B-Preview IQ2_M, the twelfth row of that roster, was mid-measurement when this was published — HumanEval 0.9451 (155/164 @8192) was in, MMLU-Pro and IFEval were still running. It gets its own paragraph and its own row when the axes land, and it will be measured under the same AR-only caveat as the Q4_K_M row it replaces.

Wall clock for the whole suite was 6,985 s (1.94 h), HumanEval 3,196 s of it and MMLU-Pro 2,047 s.

    The process failure this edition exists to correct. The run was measured and catalogued on 2026-11-08 (last axis written 02:51) and the publish pipeline ran at 04:15 the same morning. Because the report body is hand-written and the pipeline only regenerates what the documents already say, that commit (ef2b137) published the catalogue row and three charts redrawn from it — f15-quality-speed, f16-knowledge-speed, f21-profiles — with no prose, no leaderboard row and no change-log entry behind it. The site showed a point on two figures that no sentence introduced. The row is written here, the leaderboards follow from the matrix, and the counts in §9, §18.3 and §20 that had drifted by one run were recounted from the catalogue: 37 matrix rows, 155 runs, 60.6 hours, 75 aliases, 16 servable model families. The rule this points at is the one already in §4.1: the pipeline cannot publish prose it was not given, so a measured row is not a published row until the sentence exists.

    Two rendering defects fixed in passing. In Table 4b the closing note sat between the sixth and seventh rows, so the last three rows (qwen38fn-abl, Ornith-1.5-35B, ornith35b) had been rendering as literal pipe text outside the table since v1.20 — visible on every page view, unnoticed in every diff. The note now follows the table.

    The second was the renderer itself. md2html.py emitted one <li> per source line and closed the list at the first wrapped line, so every bullet longer than one line was published as a one-line list item followed by a loose paragraph: §4.1's five bullets, §21's version list and half the retirement notes came out that way, with stray ** in the HTML wherever bold crossed a wrap (393 <strong> spans before the fix, 403 after). The renderer now absorbs indented continuation lines into the item they continue, and it is published in tools/ so the pages can be rebuilt from the markdown this repository holds.

    This edition was published in three commits. 285c0a7 carried the new row, the recounted totals and the Table 4b repair; the second added §4.3 and the renderer fix above; the third rewrote §13. Between the first and the second the page was live for about an hour with the row but without the rebuild register — the same class of half-published state this edition opens by correcting, caught the same day and in the same way: by reading the rebuilt page rather than the diff.

    §13 rewritten, and one figure in it corrected. The comparison against Nvidia and Apple is now organised around the question that decides the purchase — what caps the GPU's working set — rather than around a feature matrix: VRAM (hardware, 24-32 GB), Apple's wired limit (a driver default at ~75% of RAM, 96 GB of 128, raisable with sysctl iogpu.wired_limit_mb), and GTT here (a kernel parameter, 100 GiB, with an 8 GiB carve-out unused). It adds the disk-to-GPU path for each (a PCIe copy on Nvidia, none on either UMA machine), the bandwidth arithmetic per token, the software gap on its own terms (CUDA as a platform; Metal/MLX as a narrower one; Vulkan/llama.cpp and partial ROCm here), and a failure-modes subsection, because the three machines fail on different inputs.

    The correction: v1.22's §13.2 read "this box reads 13.4 GiB per token for its driver at 59.5 t/s". 13.4 GiB is the file size. Read per token — 4B active at 4.5 bpw, so ~2.25 GB, rising to 2.5-3 GiB with attention and KV reads — the implied effective bandwidth is 134-190 GB/s, inside the 120-280 GB/s band §2.2 reports, not the 797 GB/s the old sentence implied. The decode comparison it supported (3-4× a 4090 on models that fit) survives, because it rests on the bandwidth ratio, not on that figure.

    Every number about the other two platforms is a vendor specification with the source linked, and none of them was benchmarked for this report — stated in the section rather than left for a reader to discover.

    Build identity. Every number here is fork b3-1a33095, kernel 7.3.1-1-cachyos, Mesa 26.2.5 / vulkan-radeon 26.2.5, ggml-vulkan ABI 0.25.3. The four trees rebuilt on the evening of 2026-11-08 — upstream-llama, flint and sensenova at upstream 7d7f028 (0.9.0-dev, ABI 0.29.0), prism at 6447906bf (0.7.0-dev, ABI 0.27.0) — serve nothing in this report and appear in no row. They are now tabulated in §4.3, because a reader building one of them gets a binary four ggml ABI minor versions away from the one the numbers came from; the build register remains a single-fork register until a benchmark is run, with paired reps, on one of them.

Riddles 10/14.

    BF16 of the same weights is a trap on this platform. Neither serving tree compiles coopmat2 shaders, and the Vulkan backend gates fast BF16 matmul on coopmat_bf16_support / coopmat2_bf16_support, so the identical file in BF16 runs 11.6 t/s — 7.5× slower than the K-quant. It was measured, then deleted along with a third-party DFlash draft head that refuses to load (done_getting_tensors: wrong number of tensors; expected 64, got 58). Both deletions carry their sha256s and restore recipes in the ledger; the Q4 file's hash is 1ac70791…9287f6cb.

    One operational note worth carrying forward. llama-model-guard.timer restarted the channel driver two minutes into the first Laguna window, because a transient bench-* unit is not a llama-* unit and the guard's "another unit is active, defer" rule never applied. The fix is a hold file: touch ~/llama-local/.guard-hold before stopping the driver for a benchmark, remove it after.

    Matched at n=60/40/30 the two are a tie with opposite strengths — Swift takes code (0.9167 against 0.8667) and instruction-following (0.87 against 0.77 prompt-strict), the abl takes knowledge (0.8750 against 0.8000) — three items each way, inside one standard error. No retirement follows from it: the resident file keeps its unit and Swift sits on disk as a spare for code-heavy work rather than displacing anything.

    The harness finding: IFEval has been measured at 1280 tokens, not at the cap quoted beside it. lm-eval's IFEval task defines its own max_gen_toks, which overrides the value passed in --model_args; § of this page already recorded that pin as the cause of one nonsensical historical row, and it generalises. On a thinking model it is not a rounding error: Axion scores 0.2667 prompt-strict / 0.2000 instruction-strict at the pin, and 0.7333 / 0.6444 with --gen_kwargs max_gen_toks=4096. Verified twice on the same server, same 30 items, same build — the only variable was the cap. Asked directly, "a sentence about a dog without using the letter e" cost the model 3,010 tokens and then answered correctly. Read every 4-decimal IFEval figure in this archive, including the driver's 0.93, as a 1280-token measurement; for models that terminate promptly that is enough, and for models that deliberate it is a floor.

    One arrival, kept on demand — and a footprint rule that only appears at this size.

    Groot-65B-A6B-261023 is the largest file measured here, and the model name understates it: the GGUF header declares 116,514,464,640 parameters under qwen4exp — 48 blocks, 256 experts routed 10 per token, 12 full-attention and 36 Gated DeltaNet layers, plus the per-layer embedding bank this family carries. Six files (four Q4_K_M shards, a BF16 projector and a 4.89 GiB MTP draft head) were fetched sequentially at ~45 MB/s and every one was checked against the Hugging Face tree API's lfs.oid, size and sha256.

    The number that changed the operating rules is not a score: it is MemAvailable. Served all-resident on upstream-master-bolt it pinned 71.0 GiB of GTT and left the machine with about 1 GiB available — the process then carried 21 GB of anonymous RSS and 21.7 GB of zram, and a first suite attempt (four slots, 32k context, vision projector loaded) was globally OOM-killed after seven minutes, with the kernel recording the victim's own anonymous RSS as 10 MB. GTT is unreclaimable system RAM on this box, not a separate pool, so "the weights fit the 100 GiB pool" is not the same claim as "the model fits the machine". Re-served on the halo-box fork with --load-mode mmap --lazy-mode auto it holds 50.4 GiB of GTT, runs at the same speed within noise (27.66 vs 27.43 t/s over three greedy samples), and co-exists with the driver and the boot model — measured together at GTT 73.9 GiB with 38 GiB still available.

    What it scores. Code 0.9000 (54 of 60 at cap 2048) and knowledge 0.7500 (30 of 40): both subsets, so the row carries its item counts and is ranked against other subsample rows, not against the 164/120 columns. Decode 27.6 t/s is about 1.8x slower than the 116.8B gpt-oss file at similar active size, and the weak axis is instruction-following — IFEval 0.60 prompt-strict, 0.56 instruction-strict over 30 items, against 0.93 for Qwen3-Next-80B. Riddles read 9/14, but all five misses returned exactly the 2048-token cap with empty content; re-asked at 4096 the family-relations puzzle answers correctly after 1,953 thinking tokens, so the row is deliberation length, not capability. Per-request reasoning_effort is live on this template: the same arithmetic probe costs 943 tokens at default, 95 at low, 64 at medium, 2 at none.

    The drafter result reverses a rule this page has argued for a month. Every grafted -md head measured here lost 8-11% despite 87-92% acceptance, and the standing advice was --spec-type none for MoE models. The MTP head that ships with Groot's own weights gained +28.7% (27.66 → 35.66 t/s, 76.3% acceptance, mean draft length 3.29). Provenance decides, not acceptance ratio: a head trained and exported with the trunk pays; a head borrowed from a sibling does not. Note also that this build exports no llamacpp:spec_decode_* gauges for qwen4exp — the ratio exists only in the server log.

    Verdict: kept, on demand, not adopted. The driver still leads on code, knowledge, instruction-following and speed; this is a burst model for hard reasoning and code, and the first one that can sit beside the driver while it does it. Recipe: ~/llama-local/run-groot65b.sh [nomtp|mtp], port 8182, -c 16384 -np 1 -b 1024 -ub 256, q8_0 KV, GROOT_LAZY=auto.

    The v1.16 correction. That entry recorded the 32B-A6B prune as unloadable: "header says 177 experts, tensors hold 64, the router still has 177 rows". The observation was right and the conclusion was wrong. The file has three expert banks per layer — ffn_*_exps at Q4_K/Q5_0, _tier1 at Q2_K, _tier2 at Q1_0 — and the bank dims sum to the router width exactly: block 0 is 64+60+53 = 177, block 1 is 64+60+30 = 154, block 24 is 64+41+10 = 115. Reading tier 0 alone is what made it look inconsistent, and the header patch tried in v1.16 was never the fix.
