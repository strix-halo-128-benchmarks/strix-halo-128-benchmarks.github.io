Change log — every version, and why it changed

Contents

    This document's history, kept separate from the report so the report can stay about the measurement. Each entry states what changed and the numbers that forced the change; a correction is only worth anything if it records what was wrong before it.

    Versions before 1.3 are summarised compactly: they predate the build register (§4.1), the cap discipline (§7.2) and the provenance manifest (§20.5), and their numbers should be read with those absences in mind.

    Version 1.17 (2026-11-01)

    An executive summary in plain language, and the technical one demoted to where it belongs. §0 now opens with five findings written without jargon — the small model wins, bigger is slower for no accuracy gain, coding and knowledge are separate skills, compression costs knowledge before skill, uncensoring is free when done properly — followed by what a sweep costs (0.14 kWh, about 3.5p) and an explicit "what this cannot tell you" paragraph (164 code problems and 120 knowledge questions per model, so gaps under ~5 points are noise).

    The seven technical claims that used to open the report are now §0.1, the conventions are §0.2, and the roster inventory is §0.3. Nothing was discarded: the plain version answers "what did you find" and the technical version answers "what does that mean for this hardware".

    Two corrections while rewriting it: an earlier draft called the driver "the best coder", which is not true — minicpm-v47-35b ties it at 0.9573 at cap 4096 — so the claim is now "joint-first on code, first on knowledge among models on disk"; and the recommendation list named a model that has since been deleted.

    Version 1.16 (2026-11-01)

    The week's most interesting shape does not load, and the reason is in the file. Qwen3.8-Flash-Next-32B-A6B "Prune2" (48.31 GiB, qwen4exp, 32B total / 6B active) was fetched to test the one gap in this roster — an active-parameter count between the driver's 4B and the 120B class's 12B. It fails in both trees:

    check_tensor_dims: 'blk.0.ffn_down_exps.weight' expected 640, 2560, 177, got 640, 2560, 64, 1

    The header claims 177 experts, the expert tensors hold 64, and the router still has 177 rows — so no single expert_count satisfies the file. Patching the header to 64 moves the error one tensor along to ffn_gate_inp, which is the proof that the export is internally inconsistent rather than mistagged. Recorded in the not-runnable reference, deleted with its hash, and noted in the ledger so nobody re-downloads 48 GiB to rediscover it. A re-export with matching counts would be worth testing on shape alone.

    That makes three arrivals measured or rejected today (Dark-Craving, Holo4, this one) and none added: the roster is 17, at 630 GiB.

    Version 1.14 (2026-11-01)

    A provenance manifest, and licences stated for the first time. §20.5 lists every servable artefact with its upstream repository and the licence the card declares, and records which bytes are provably upstream's: 13 of 17 artefacts verify by sha256 against the repository's LFS object id, re-computed on disk rather than copied from the fetch log. The four that do not are named rather than filled in — they predate the record, and their hashes are in data/provenance.json so anyone can close the gap in a minute.

    That closes the largest hole in a document about reproducibility: it described 30 models' behaviour in detail while never saying where a single file came from or what licence governed it.

Figures carry <title>/<desc> taken from their own captions.

    Version 1.12 (2026-11-01)

    A per-axis leaderboard page, generated from this matrix. leaderboards.html ranks the same 30 rows five ways — HumanEval, MMLU-Pro, reasoning traps, decode, prefill — with cap, item count, build and date on every line, and a separate table for the one sub-2048 floor so a floor is never ranked against a ceiling. It is generated by scripts/leaderboards.py from the sanitised report, not hand-written, so the two views cannot disagree; the build gate refuses to publish if either page stops linking the other.

    Deliberately absent: a composite index (weighting code against knowledge requires assumptions this report will not make for the reader) and a per-watt ranking (power is measured in §15 but not paired with throughput per model, so any such number would be invented).

    Version 1.9.2 (2026-10-31)

    Storage named, and bounded. §2.3 records the drives (BIWIN X570 PRO 4 TB for system and models, a Netac 2 TB spare) and the zram swap device, and states plainly what they do and do not affect: load time, not decode. Decode is LPDDR5X-bandwidth-bound and prefill is shader-bound, so no figure in this report depends on the SSD — which is worth saying, because "faster NVMe makes local LLMs faster" is a common and wrong inference. Paging being compressed RAM rather than disk is called out for the same reason.

    Version 1.9.1 (2026-10-31)

    The hardware is now named. The report described "this machine" throughout, because the sanitiser replaced the hostname; that over-corrected, since the chassis model is public product information and is the first thing a reader needs to place the numbers. It is now stated as a Minisforum MS-S1 MAX with the DMI values that prove it (product_family, product_name, sys_vendor, board, BIOS, EC) in the header and §2. The hostname, addresses and paths remain unpublished.

    Version 1.9 (2026-10-31)

    Version 1.7 (2026-10-31)

    Prior art, and the context curve that was missing. Reading two other public datasets — lhl's llama-bench sweeps and pepuscz's Flash-class results — made two gaps obvious and both are now closed or named:

    • §23 prior art. Four sources tabulated with what each answers and what it does not, plus §23.1 on

    the single model measured by both (Qwen3.8-Flash-Next: their 465/42.8 t/s at Q4_XL on Ubuntu vs this report's 448/52.9 at IQ3_S on CachyOS — different quant, consistent result). Their 30-item quality suite cannot rank models because one item is 3.3 pp; that is the gap 164 HumanEval items fills.

    • §23.2 context curve. The open item about no 32k needle is closed for the deployed driver: five

    depths from 1.8k to 112.9k prompt tokens, retrieval PASS at every one, prefill 1715 → 670 t/s and decode 57.2 → 37.7 t/s. The practical rule is to compact before 64k, not at the window edge.

    • §23.3 cross-validation. Their published 30-item suite, run unchanged on the deployed driver:

    30/30 (coding 10/10 executed against their own gold_test, GSM8K 10/10, math 10/10) — the same score their Qwen3.8-Flash-Next deployment reported. The first pass read 26/30 and all four misses were harness defects: a last-number grader that scored "$64 for the 16 glasses" as 16, a LaTeX comparison that read −2/3 as different from -\frac{2}{3}, a \boxed{} regex that truncated \frac{20}{3}, and a fixture whose gold_answer for math_08 says 20 where the correct value is 20/3 — a correction the source itself documents.

    • New tooling. ~/bench/ctxcurve.py produces the curve against a live server (no reload, no unit

    change), and ~/bench/lucebox30.py runs the published 30-item suite from Luce-Org/lucebox so the two datasets can be cross-checked on the same model. Both record per-item evidence, not just verdicts.

    Version 1.6 (2026-10-31)

    Every row now says when it was measured. Tables 4 and 4b gained a measured column — the date of the best-scoring run for that row, derived by joining each row's HumanEval and MMLU values (with their caps) against ~/runs/catalogue.json and taking that run's timestamp. 28 of 28 matrix rows and 16 of 16 servable rows resolved; the one row with no HumanEval cell (Ling-3.0-flash) was dated from its MMLU value alone.

    The join is scripted, not typed: two rows scoring identically at the same cap would have been a coin-flip, so the derivation prefers name overlap and then the most recent run, and it is re-runnable against the catalogue. What the column does not tell you is the model's release date, only when this box measured it — the spread runs from 2026-10-10 to 2026-10-31.

    Three rows in Table 4 were wrong, and are fixed:

    1. qwen3next-q6 was published as 0.9207 (164@2048). No run supports it: its best is **0.9296 over

    142 items**, and 0.9207 is ornith-mtp-21g's figure, copied onto it. Symptom to watch for: two unrelated models with a score identical to four decimals.

    1. nemotron-super-120b was published as 0.9329 (164@4096). Its runs read 0.9512 (156/164) and

    0.9470 (154/164) at that cap; the printed figure matched neither.

    What was deliberately not changed. §10's family-spread analysis, §13's platform comparison, §14's hosted comparison, §15's power section, §16's abliteration analysis and §17's DeepSeek deployment analysis were left alone: none of their inputs moved, and re-cutting them would mix a roster change into an argument about method. Rows for deleted models are retained throughout, marked ✗ with the retirement date, because a table that silently drops its losers cannot be audited.

    Figures rebuilt, and four pipeline bugs fixed. §19's ten figures were regenerated from the rebuilt catalogue, and doing it accurately turned up three defects that had been silently distorting them: (a) charts.py merged every run under one alias, so the Q8_0 gemma and the QAT file collapsed into each other and both ornith35b files did too — it now canonicalises one name per weight file, and figure 19's fourth pair is a real Q8_0→QAT comparison instead of a file against itself; (b) it took the latest run per axis rather than the best, contradicting §9's stated rule — it now takes the best, so figures and Table 4 agree; (c) §8's poisoned-MMLU rule was applied by deleting the whole run rather than the cell, so qwen38fn-abl's good HumanEval row (0.8476) disappeared from every figure along with its 1/120 MMLU — the filter now blanks the axis and keeps the rest; (d) runs-catalogue.py read the FIRST row of each axis, and IFEval writes an empty n=0 row before its scored n=30 row, so every IFEval score in the catalogue was being dropped — fixed, which is why the live driver now appears in figures 18 and 21. Figure 23 also used to plot the retired flint40b-abl run, whose 1-second samples had aged out of the 72 h raw window so it could no longer be rebuilt; it now plots the 2026-11-01 Kimi-Linear full suite, the longest run still inside that window.

    Known open items. qwen38fn-abl's MMLU-Pro cell is a poisoned 1/120 rather than a score, and it cannot be re-measured without stopping the driver (the file is 78.1 GiB, past the pool beside a resident model), which this project does not do; and the driver's context curve (§23.2) now covers 32k, 64k and 113k prompts — but no other model on disk has been measured beyond an 8k needle since the kernel moved to 7.3.0-5.
